The server side is enabled by default. `usePGlite()` is auto-imported in your server code and resolves to a single PGlite instance, created on first use and closed when the server shuts down.

```ts [server/api/hello.get.ts]
export default defineEventHandler(async () => {
  const pg = await usePGlite()
  return pg.query('SELECT now()')
})
```

## The config file

Extensions, setup code and anything else that cannot be written as plain JSON in `nuxt.config.ts` go in `server/pglite.config.ts`. It is optional; without it the instance uses the [`nuxt.config` options](/server/options).

```ts [server/pglite.config.ts]
import { citext } from '@electric-sql/pglite/contrib/citext'
import { vector } from '@electric-sql/pglite-pgvector'

export default definePGliteServerConfig({
  extensions: { citext, vector },
  init: async (pg) => {
    await pg.exec('CREATE EXTENSION IF NOT EXISTS vector')
  },
  dispose: async (pg) => {
    // runs before the instance is closed on server shutdown
  },
})
```

`definePGliteServerConfig` is auto-imported. It accepts [PGlite's own options](https://pglite.dev/docs/api#options) (`dataDir`, `extensions`, `debug`, `relaxedDurability`, …) plus `init`, `dispose` and [`devtools`](/devtools/actions).

### Extensions

Import an extension from its package and add it to `extensions`, as you would with `PGlite.create()`. `usePGlite()` is typed from the config, so an extension that adds a namespace shows up on the instance:

```ts [server/pglite.config.ts]
import { live } from '@electric-sql/pglite/live'

export default definePGliteServerConfig({
  extensions: { live },
})
```

```ts [server/api/count.get.ts]
export default defineEventHandler(async () => {
  const pg = await usePGlite()
  pg.live // typed, because `live` is in the config
  return pg.query('SELECT count(*) FROM todos')
})
```

Postgres extensions such as `vector` still need `CREATE EXTENSION`, which is what `init` is for.

### Prepare the instance with `init`

`init` runs once per created instance, before any `usePGlite()` call receives it: the place for `CREATE EXTENSION`, schema setup or seeding.

```ts [server/pglite.config.ts]
export default definePGliteServerConfig({
  init: async (pg) => {
    await pg.exec(`
      CREATE TABLE IF NOT EXISTS todos (
        id serial PRIMARY KEY,
        title text NOT NULL
      )
    `)
  },
})
```

Use the `pg` it receives: calling `usePGlite()` from inside `init` fails with a pointer instead of waiting for itself. If `init` throws, the instance is closed and the next `usePGlite()` tries again.

`dispose` runs before the instance is closed through the module, which happens when the Nitro server shuts down.

### Per-environment settings

`$development`, `$production` and `$test` keys work in the config file as they do in `nuxt.config.ts`. In that environment, the keys they set replace the top-level ones (a shallow merge):

```ts [server/pglite.config.ts]
import { vector } from '@electric-sql/pglite-pgvector'

export default definePGliteServerConfig({
  extensions: { vector },
  $development: { dataDir: 'memory://' },
  $test: { dataDir: 'memory://' },
})
```

`$test` wins over the other two while testing.

### Data directory

The data lives in `.data/pglite` under your project unless you say otherwise. There are three places to set it, from the most static to the most dynamic:

| Where | Resolved from | Use it for |
| --- | --- | --- |
| `pglite.server.options.dataDir` in `nuxt.config.ts` | the project root, at build time | a path inside the project |
| `dataDir` in `server/pglite.config.ts` | the working directory, at runtime | a path decided by code |
| `NUXT_PGLITE_DATA_DIR` | the working directory, at runtime | a path chosen at deploy time; wins over both |

PGlite's own schemes (`memory://`, …) are passed through untouched.

## Disabling the server side

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  pglite: {
    server: { enabled: false },
  },
})
```

Nothing of PGlite is then in the server bundle. `#pglite/server` still resolves, to a stub whose `usePGlite()` rejects with a pointer, so a leftover import fails clearly at runtime rather than at bundling. The [development socket](/socket) keeps working: that is the [PGlite in dev, Postgres in prod](/socket/development-only) recipe.
