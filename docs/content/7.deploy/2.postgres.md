Without a platform that applies migrations itself, the pattern is the default one: the [development socket](/socket) exports `DATABASE_URL` in `nuxt dev`, your host's environment sets it in production, and your build applies the migrations before the new code goes live.

## `DATABASE_URL`

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['nuxt-pglite'],
  pglite: {
    server: {
      enabled: false,
      socket: { port: 5433 }, // exports `DATABASE_URL` in `nuxt dev`
    },
  },
})
```

```ts [server/utils/db.ts]
import { drizzle } from 'drizzle-orm/node-postgres'

import { relations } from '../database/relations'

export function useDB() {
  return drizzle(process.env.DATABASE_URL!, { relations })
}
```

Set `DATABASE_URL` in your host's environment to any Postgres reachable from it: [Supabase](https://supabase.com), [Railway](https://railway.com), a managed instance or your own server, scoped to the server runtime (and to the build, if it migrates). Use the pooled connection string when your provider has one: serverless functions open many short-lived connections.

## Migrations in the build

Keep the migration files where drizzle-kit writes them, apply them locally from `init` with [`applyMigrations`](/migrations), and apply them to the real database from the build command, which runs with `DATABASE_URL` set:

```ts [drizzle.config.ts]
import { defineConfig } from 'drizzle-kit'

export default defineConfig({
  schema: './server/database/schema.ts',
  out: './server/database/migrations',
  dialect: 'postgresql',
  dbCredentials: {
    // the real database in the build, the development socket otherwise
    url: process.env.DATABASE_URL ?? 'postgres://postgres@127.0.0.1:5433/postgres',
  },
})
```

```json [package.json]
{
  "scripts": {
    "build": "drizzle-kit migrate && nuxt build"
  }
}
```

`drizzle-kit migrate` keeps its own bookkeeping (`drizzle.__drizzle_migrations`), separate from the one `applyMigrations` keeps locally (`netlify.migrations`): each database is tracked by the tool that migrates it, from the same files. To use one tool on both sides instead, run [`applyMigrations` with `fromPool`](/migrations#against-postgres) from a script in the build command.

## Other hosts

The same pattern works on any host Nitro supports (Vercel, a Node server, a container, …): the build contains your driver and reads `DATABASE_URL`, the host provides it. Only the build settings differ; see [Nuxt's deployment guide](https://nuxt.com/docs/getting-started/deployment).

## Neon

[Neon's](https://neon.tech) serverless drivers (`drizzle-orm/neon-http`, `drizzle-orm/neon-serverless`) speak HTTP and WebSocket to Neon's proxy, not the Postgres wire protocol, so they cannot reach the development socket. Use `node-postgres` in development and switch on `import.meta.dev`, which the bundler replaces, so only the production driver is in the build:

```ts [server/utils/db.ts]
import { drizzle as drizzleNeon } from 'drizzle-orm/neon-http'
import { drizzle as drizzlePg } from 'drizzle-orm/node-postgres'

import { relations } from '../database/relations'

export function useDB() {
  const url = process.env.DATABASE_URL!
  return import.meta.dev ? drizzlePg(url, { relations }) : drizzleNeon(url, { relations })
}
```

Or connect to Neon with `pg` in production too, through its standard connection string. On [Netlify Database](/deploy) the switch is done for you: `drizzle-orm/netlify-db` uses Neon's serverless driver unless `NETLIFY_DB_DRIVER` is `server`, which the socket's `netlify` preset exports.

## PGlite in production

If you deploy with the server side **enabled**, PGlite itself runs in production and needs a writable, persistent data directory: a Node server or a container with a volume, not a serverless function. Set it with [`NUXT_PGLITE_DATA_DIR`](/server/options#runtime-overrides), and keep `applyMigrations` in `init` pointed at a directory that exists at runtime (see [Migrations](/migrations)).
