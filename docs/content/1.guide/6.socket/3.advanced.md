PGlite is a single Postgres backend: one session, one connection's worth of state. The socket lets many clients use it by taking turns, and they share that session. For the usual development workload (an app's pool, a migration tool, `psql`), this behaves like a server. The details below matter when something does not.

## One owner at a time

A client owns the database for the length of a transaction or pipeline; the others queue until it is done. The process's own `db.query()` / `db.transaction()` calls (a `server` action, the DevTools SQL box) queue the same way, so neither side's statements land inside the other's transaction.

An owner that stays idle inside a transaction or pipeline for longer than [`idleInTransactionTimeout`](/guide/socket/options) is disconnected, which rolls its transaction back and lets the queue move. It is off by default; set it if a crashed tool or a forgotten `BEGIN` in `psql` can stall your app.

A client that holds a transaction open and waits for another client's query therefore waits forever: that query runs only once the transaction ends. A test that holds a lock on one connection and inspects it (`pg_locks`, `pg_stat_activity`) from a second one stalls this way, and `idleInTransactionTimeout` only turns the stall into an error, with the transaction rolled back and its locks gone. Run the probe on the connection that holds the transaction, or run the test against a real Postgres.

## Session state

When a client disconnects, its prepared statements and `LISTEN` subscriptions are dropped. Settings, temp tables and advisory locks belong to the session every connected client shares, so they are dropped once the last client has disconnected, as a real server would with the connection: the next client starts with a clean session. The settings the process set before the socket started (for example a `SET search_path` in `init`) are put back then.

Notifications reach the clients that ran `LISTEN` on the channel, and no others.

## Known differences

Inherent to sharing one session:

- `COPY … FROM STDIN` is refused with SQLSTATE `0A000`: PGlite cannot run it.
- Every client is the same backend: one `pg_backend_pid()`, one row in `pg_stat_activity`, settings and temp tables visible to every client, and advisory locks that never conflict between clients. A lock a client never unlocked stays held until the last client disconnects.
- `LISTEN` / `UNLISTEN` and SQL-level `PREPARE` / `EXECUTE` / `DEALLOCATE` are recognised as single statements, the way drivers send them. `LISTEN` takes effect regardless of the transaction it ran in.
- Temp tables and advisory locks taken by the process itself are released when the last client disconnects.
- Connections are not authenticated, and every database name reaches the same database.

## The config file outside the bundle

The socket imports `server/pglite.config.ts` in the Nuxt process through [jiti](https://github.com/unjs/jiti), not through Nuxt's bundler, with the app's aliases: `~~`, `#pglite/migrations` and the aliases of other modules resolve as they do in the server bundle. `definePGliteServerConfig` is provided as a global while it loads, so a file written for the server works unchanged; other auto-imports are not available there.

## When `init` fails

The instance is created, and `init` (migrations, seeding) run, when `nuxt dev` starts. If either fails, the dev server keeps running: the error is logged, the socket listens at its usual URL with its variables exported, and every client is refused with a FATAL `57P03` (`cannot_connect_now`) error, `PGlite is not ready: <the error>`, whose hint points at the fix. Your app's routes then fail with that message rather than with a connection error, and the [DevTools tab](/guide/devtools#when-init-fails) shows the reason.

Restart `nuxt dev` once the cause is fixed (a change to the config file restarts it), or run the [`reset-database` action](/guide/devtools/actions#reset-database) to start from an empty database.

## Bun and Deno

The socket uses only Node built-ins (`node:net`, `node:fs`), so it runs wherever `nuxt dev` does, including Bun and Deno. It has been tested with `pg`, postgres.js, `psql` and `drizzle-kit push` on all three. To serve PGlite without Nuxt, see [Outside Nuxt](/recipes/outside-nuxt/socket).
